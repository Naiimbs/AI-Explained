AI Model ≠ Tool: شكون يعمل شنوّة؟

الفرق بين العقل المفكر والأداة المنفذة

🧠

الـAI Model (النموذج)

The Reasoner / Decision Maker
  • فهم طلب المستخدم والمقصد (Intent).
  • تحليل الـContext والمعطيات المتوفرة.
  • اختيار الأداة المناسبة من قائمة الأدوات المتاحة.
  • تجهيز الـParameters واستخراج القيم (مثل order_id: 1024).
  • قراءة النتيجة (Result) وتفسيرها بلغة طبيعية.
🔧

الـTool / Application (الأداة)

The Executor / Real World Bridge
  • استقبال الـPayload من الـAI بدقة.
  • الاتصال بقاعدة البيانات أو الـAPI الخارجي.
  • تنفيذ العملية الفعلية (Query, Write, Update).
  • إرجاع النتيجة (Result Data) إلى الـAI Model.
  • حماية النظام: الـAI ما عندوش وصول مباشر للـDatabase!
🔄 دورة الحياة الكاملة

What is Tool Calling? (الخطوات الخمس)

كيفاش يتحول طلب المستخدم من كلام إلى تنفيذ حقيقي ثم جواب نهائي

01. REQUEST
المستخدم يطلب: « وين وصلت طلبيتي رقم 1024؟ »
02. DECIDE
الـAI يفهم ويقرر أنه يحتاج أداة خارجية: get_order(order_id: 1024)
03. EMIT CALL
الـAI يبعث للـApplication هيكل برمجي (JSON Tool Call) محدد ودقيق.
04. EXECUTE
الـApplication ينفذ الدالة، يجيب المعلومة من قاعدة البيانات، ويرجع Result للـAI.
05. ANSWER
الـAI يستلم النتيجة ويصيغها: « الطلبية خرجت للتوصيل ومن المفروض توصل اليوم ✓ »
💻 مثال تقني تطبيقي

Technical Example: ماذا يتبادل الـAI والسيرفر؟

ما تقلقوش، موش كود معقد.. الهدف نشوفو أول مرة شنوّة يصير فعلياً وراء الكواليس

1. طلب من الـAI
JSON Call
{
  "tool": "get_order",
  "arguments": {
    "order_id": 1024
  }
}

الـAI ما يكتبش كلام إنشائي؛ يرسل طلباً هيكلياً: "استعمللي أداة get_order للطلب 1024".

2. تنفيذ التطبيق
App Logic
# السيرفر ينفذ الدالة
def get_order(order_id):
  return db.get_order(order_id)

تطبيقنا هو الذي يتصل بقاعدة البيانات ويجلب السجل الحقيقي بأمان وصلاحيات محكمة.

3. النتيجة للـAI
Result JSON
{
  "order_id": 1024,
  "status": "shipped",
  "carrier": "DHL",
  "estimated_delivery": "2026-09-06"
}

النتيجة ترجع للنموذج ليفهمها ويصيغ الجواب النهائي للإنسان: "الطلبية خرجت وموعدها غدوة".

🔄 مسار الرحلة الكامل (The Full Execution Flow)
User Request ➔ AI decides tool ➔ Tool Call (JSON) ➔ App executes ➔ DB / API ➔ Tool Result ➔ AI generates response

⚠️ تمييز معماري حاسم

The AI Decides ➔ The Application Executes

الـAI لا يملك سحراً للدخول المباشر إلى خوادمك

الـAI Model ما دخلش وحدو لقاعدة البيانات وما نفّذش كود SQL بطريقة سحرية.
الـAI قام بأمر واحد فقط: طلب استعمال أداة (Requested Tool Execution).
👤 User ➔ 🧠 AI Model ➔ 🔧 Tool Call ➔ 💻 Application ➔ 🗄️ Database / API
🔒 هذا هو سر الأمان والتحكم: تطبيقك هو الحارس (Gatekeeper) الذي يتحكم في ما يُنفّذ وما يُرفض.

ماذا لو فشلت الأداة؟ (Tool Failures)

الـTool Result ليس دائماً 200 OK.. كيف يتصرف الـAgent الذكي؟

❌

النظام الجامد (Fragile Bot)

يتوقف فوراً ويقول: "عذراً، حدث خطأ في النظام لا أستطيع مساعدتك."

« لم أجد الطلبية #1024، هل يمكنك التأكد من الرقم أو كتابة بريدك الإلكتروني؟ »

[OPENING] · شريحة 00 (المدخل)
في الحلقة اللي فاتت، حكينا على كيفاش الـAI Agent يخدم. قلنا اللي الـAgent ياخذ Goal، يفهم شنوّة المطلوب، يعمل Plan، وبعد يبدأ يتصرف. أما توا فما سؤال مهم برشا: كيفاش الـAgent يعمل حاجة في العالم الحقيقي؟ مثلاً، لو نقولو للـAgent: "شوفلي وين وصلت الطلبية متاع Ahmed." هل الـAI عندو access مباشر للـdatabase؟ هل ينجم يدخل وحدو للـShopify؟ هل ينجم يبعث email؟ هل ينجم يبدّل information؟ الإجابة هي: لا، موش وحدو. وهنا تجي واحدة من أهم الـconcepts في الـAI Agents: Tool Calling.
[RECAP] · شريحة 01
قبل ما نفهمو Tool Calling، خلينا نرجعو بسرعة للحلقة اللي فاتت. الـAgent يخدم تقريباً هكّا: Goal → Understand → Plan → Act → Observe مثلاً، user يقول: "الطلبية متاع Ahmed تأخرت، شوفلي المشكلة." الـAgent يفهم الـgoal. وبعد يقرر: أول حاجة، نلقى الـorder. بعد نشوف الـstatus. بعد نشوف delivery information. وبعدها نقرر شنوّة يلزم نعمل. أما هنا يجي السؤال: كيفاش باش نلقى الـorder أصلاً؟ الـAgent يحتاج capability تخليه يتعامل مع الـsystem. وهنا نستعملو الـTools.
[WHAT IS A TOOL?] · شريحة 02
ببساطة شديدة: Tool هي capability نعطيوها للـAI باش يعمل action أو يجيب information من system خارجي. مثلاً، نجم نعطي للـAgent Tool اسمها: get_order Tool أخرى: search_customer Tool أخرى: track_delivery Tool أخرى: create_ticket أو حتى: send_email يعني الـAI عندو brain... والـTools نعطيوه تقريباً الـhands.
[SIMPLE EXAMPLE] · شريحة 03
تصور عندك شخص ذكي برشا. نعطيه عقل. نعطيه instructions. ونعطيه knowledge. أما نحطوه في غرفة وما نعطيوه حتى access لأي system. هو ينجم يفكر. ينجم يحلل. ينجم يجاوب. أما ما ينجمش يعمل برشا حاجات في العالم الخارجي. إذا نعطيوه calculator، ينجم يحسب. إذا نعطيوه access للـdatabase، ينجم يجيب information. إذا نعطيوه email tool، ينجم يبعث email. إذا نعطيوه calendar tool، ينجم يتعامل مع الـcalendar. إذن: Tools extend what the AI can do.
[AI MODEL VS TOOL] · شريحة 04
وهنا فما distinction مهم لازم نفهموه. الـAI Model مسؤول على حاجات كيف: فهم الـrequest. تحليل الـcontext. اختيار شنوّة يلزم يعمل. واختيار الـtool المناسبة. أما الـTool هي اللي تعمل العملية فعلياً. مثلاً: الـAI يفهم: "باش نحتاج information على order number 1024." فيقرر يستعمل: get_order ويبعت request فيها: order_id: 1024 الـapplication متاعنا ياخذ الطلب هذا. يمشي للـdatabase. يجيب المعلومات. وبعد يرجع النتيجة للـAI. والـAI يستعمل النتيجة باش يكمل المهمة. وهذا هو تقريباً مفهوم: Tool Calling.
[WHAT IS TOOL CALLING?] · شريحة 05
خلينا نشوفوها step by step. المستخدم يقول: "وين وصلت الطلبية #1024؟" الـAI يفهم اللي يلزمو information على order 1024. بعد يقرر: "I need the get_order tool." فيعمل Tool Call. يعني يطلب من الـapplication: استعمل Tool اسمها get_order بـinput: 1024 الـapplication ينفذ الـtool. الـdatabase ترجع مثلاً: Order #1024 Status: Shipped Carrier: DHL Expected delivery: Today النتيجة ترجع للـAI. والـAI يفسرها للمستخدم: "الطلبية خرجت للتوصيل ومن المفروض توصل اليوم." هنا صار Tool Call.
[TECHNICAL EXAMPLE] · شريحة 06 (مثال تقني)
توا خلينا نشوفو نفس الفكرة، أما بطريقة تقنية شوية. ما تقلقوش، ما باش ندخلوش في code معقد. نفترضو عنا Tool اسمها: get_order والـTool هذي تستقبل order_id. مثلاً الـAI قرر يستعملها للطلبية رقم 1024. الـAI ما يبعثش للمستخدم: "Order 1024." هو يبعث للـapplication Tool Call بالشكل هذا تقريباً: { "tool": "get_order", "arguments": { "order_id": 1024 } } شنوّة صار هنا؟ الـAI قال للـapplication: "استعمللي الـget_order tool، والـorder_id هو 1024." الـapplication توا ينفذ الـfunction متاعنا: def get_order(order_id): return database.get_order(order_id) تمشي للـdatabase وتجيب المعلومات، والـresult يرجع هكّا: { "order_id": 1024, "status": "shipped", "carrier": "DHL", "estimated_delivery": "2026-09-06" } الـresult هذا يرجع للـAI، والـAI توا عندو information حقيقية يقدر يستعملها في الإجابة: "الطلبية متاعك خرجت للتوصيل، والموعد المتوقع هو غدوة." لاحظو الـflow: User Request ➔ AI decides to use a tool ➔ Tool Call ➔ Application executes ➔ Database / API ➔ Tool Result ➔ AI generates the response. الـAI ما عملش database query وحدو، هو اختار الـTool وحدد الـinputs، والـapplication هو اللي نفذ العملية ورجع الـresult. وهذا هو الفرق بين: AI generating text و AI interacting with a system.
[IMPORTANT POINT] · شريحة 07
وهنا نحب نوقف على نقطة مهمة برشا. الـAI ما دخلش وحدو للـdatabase. وما نفذش العملية بطريقة سحرية. الـAI طلب استعمال Tool. والـapplication متاعنا هو اللي نفذ الـTool. يعني تقريباً: User ثم AI Model ثم Tool Call ثم Application ثم Database أو API ثم Tool Result ثم AI Model ثم User. إذن: The AI decides what tool to use. أما: The application executes the tool. وهذي نقطة أساسية في architecture متاع الـAgents.
[REAL E-COMMERCE EXAMPLE] · شريحة 08
خلينا ناخذو مثال أقرب للواقع. عندنا customer اسمو Ahmed. وعندو: Order number 1024. Ahmed يقول: "طلبيتي ما وصلتش." نحب الـAgent يساعدو. أول حاجة، الـAgent يحتاج يعرف معلومات الطلبية. فيستعمل: get_order ويرجع مثلاً: Order #1024 Status: Shipped Carrier: DHL الـAgent توا يعرف اللي الطلبية خرجت من المخزن. أما مازال ما يعرفش وين وصلت. إذن يحتاج Tool أخرى. يستعمل: track_delivery ويعطيها tracking number. الـTool ترجع: Package delayed. Current location: Tunis. New estimated delivery: Tomorrow. الـAgent توا عندو information كافية. فيقول للمستخدم: "الطلبية متاعك خرجت من المخزن، أما صار delay في التوصيل. الموعد الجديد هو غدوة." لاحظو شنوّة صار. الـAgent ما كانش عندو الجواب من البداية. هو استعمل Tools باش يجمع الـinformation اللي يحتاجها.
[MULTIPLE TOOLS] · شريحة 09
وهنا نصلو لحاجة أهم. الـAgent عادة ما يكونش عندو Tool وحدة. ينجم يكون عندو مجموعة كاملة. مثلاً: search_customer get_order track_delivery create_ticket send_email update_order وهنا الـAgent ينجم يربط أكثر من Tool في نفس المهمة. مثلاً المستخدم يقول: "الطلبية متأخرة. إذا تأكدنا اللي المشكلة من delivery، افتحلي support ticket." الـAgent ينجم يعمل: أولاً: get_order بعد: track_delivery يشوف النتيجة. يحللها. إذا فعلاً فما delivery problem: create_ticket وهنا ولّينا نشوفو الفرق الحقيقي بين chatbot عادي وAgent. موش فقط: Question → Answer أما: Goal → Tool → Result → Decision → Next Tool
[WHAT IF THE TOOL FAILS?] · شريحة 10
أما طبعاً، موش كل Tool Call تنجح. مثلاً: الـAgent يعمل: get_order(1024) والـsystem يرجع: "Order not found." شنوّة يعمل الـAgent؟ ما يلزمش بالضرورة يوقف ويقول: "Sorry, I can't help." ينجم يفهم اللي ممكن رقم الطلبية غلط. ويسأل المستخدم: "تنجم تتأكدلي من رقم الطلبية؟" هنا تبدأ تشوف حاجة مهمة: الـAgent ياخذ result. يفسر الـresult. وبعد يقرر شنوّة يعمل. وهذا باش يقودنا للحلقة الجاية.

[UX PERSPECTIVE] · شريحة 12
وبالنسبة ليا كـUX Designer، هنا الموضوع يولي interesting برشا. خاطر كي نعطيو الـAI Tools، إحنا موش فقط نقرروا: What can the AI say? إحنا زادة نقرروا: What can the AI do? وهذا فرق كبير. مثلاً: Tool اسمها: search_orders ممكن تكون relatively safe. أما Tool اسمها: cancel_order هذي action عندها consequence حقيقية. إذن لازم نسألو: هل الـAgent ينجم يعملها وحدو؟ ولا لازم confirmation من المستخدم؟ هل المستخدم يشوف شنوّة باش يصير؟ هل نجموا نعملو Undo؟ شنوّة يصير إذا الـTool تفشل؟ وشنوّة permissions عند الـAgent؟ مثلاً قبل ما يعمل: "Cancel order #1024" ممكن نطلب من المستخدم: Confirm قبل التنفيذ. وهنا UX متاع الـAgent يولي مهم جداً.
[KEY IDEA & CLOSING] · شريحة 13
إذن، خلينا نلخص الحلقة. AI Model = Brain Tools = Capabilities و: Tool Calling = The bridge between AI and the real world. الـAI وحدو ينجم يفهم، يحلل، ويجاوب. أما الـTools هي اللي تعطيه القدرة باش يتعامل مع systems حقيقية. والعملية تقريباً هكّا: Decide → Call Tool → Get Result → Use Result --- أما توا فما سؤال جديد. إذا الـAgent عمل Tool Call... وخذا Result... شنوّة يعمل بعد؟ هل يرجع مباشرة للمستخدم؟ ولا يستعمل Tool أخرى؟ ولا يبدل الـPlan؟ ولا يسأل سؤال؟ ولا يعاود المحاولة؟ يعني كيفاش الـAgent يعرف شنوّة هي الخطوة الجاية؟ وهنا ندخلو في concept مهم جداً: The Agentic Loop. في الحلقة الجاية باش نشوفو كيفاش الـAgent يعمل: Think → Act → Observe → Decide → Act Again حتى يوصل للـGoal. نشوفكم في Episode 4.
